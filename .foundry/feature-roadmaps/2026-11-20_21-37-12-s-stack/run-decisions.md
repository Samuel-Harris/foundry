The orchestrator records here the decisions taken while the s-stack package is built. Read this file together with `decisions.md`.

| Date | Decision | Door | Reason |
| --- | --- | --- | --- |
| 2026-11-21 | The tick fires at minutes 7, 27 and 47 of each hour. | Two-way | Twenty minutes apart, and off the busy minutes on the hour and half hour. |
| 2026-11-21 | The run's workflow is driven by hand, with the briefs the developer wrote, until the launcher and `sam-mode` exist. | Two-way | The developer's instruction for this run. |
| 2026-11-21 | The 2,500-line pull request limit does not count auto-generated files such as `apm.lock.yaml`. The PR that adds `packages/s-stack` and the `default-stack` PR proceed with their full lockfiles, and each description states the hand-written line count. | Two-way, asked because the coding rules require it | The developer: "The 2500 line PR limit should ignore auto-generated config like lockfiles". Raised by the planner. |
| 2026-11-21 | The orchestrator branch for this run is `s-stack-package`, not `s-stack` as `workflow.md` would name it. Phase branches are `s-stack-phase-<phase>`, cut from `s-stack-package`. | Two-way | The roadmap was written and pushed as pull request 76 on `s-stack-package` before the run started. |
| 2026-11-21 | For this run, a commit that touches only generated files (`**/apm.lock.yaml` and the `version:` line of `packages/*/apm.yml`) does not move the code head and cancels no verdict. A stale lockfile or version on a pull request branch is a regenerate-only fix round. The PR creator refreshes the regenerate commit and repeats the equality proof, the phase stays in PR, and neither gate runs again. This amends `workflow.md` States rule 5 for this run. | Two-way | The developer chose the planner's option B. Without it, each of eight or more merges into `main` would send every other open phase back through both gates on unchanged code. The pre-commit hook, CI's frozen-lockfile and versioning checks, and Tier 1 on every merge into `s-stack-package` still catch a bad regeneration. |
| 2026-11-21 | When merging `main` into `s-stack-package` conflicts only in generated files (`**/apm.lock.yaml` and `version:` lines), the orchestrator resolves it on `s-stack-package`. It takes `main`'s side, reinstalls, relativises and runs Tier 1 before it commits. A conflict in any hand-written file still goes to the phase session that owns the paths. This amends the `workflow.md` Branches rule that the orchestrator never resolves a conflict. | One-way, asked | The developer chose it. Routing a generated-file conflict through a phase branch would put `main`'s changes in that phase's diff and break the equality proof. |
| 2026-11-21 | Each merge of an s-stack pull request into `main` may create a public `s-stack--v0.1.x` tag for a package that is not yet complete. | One-way, asked | The developer accepted it. The package is pre-1.0, and no consumer installs it until `default-stack` depends on it in the last phase. |
| 2026-11-21 | After any merge into `main` that touches `packages/`, the orchestrator sends a generated-only fix round to every open s-stack pull request and marks it as needing an update on the status board. A pull request is ready to merge only when its checks ran after `main`'s current tip. | Two-way | Pull request CI does not rerun when `main` moves, and two pull requests that raise the same version merge cleanly and then break the push check and the tag job. |
| 2026-11-21 | The feature plan merged at `a66024b` with two known gaps in C7, both sent back to the planner: merging `main` cleanly into `s-stack-package` skips the hook and Tier 1, and the squash-merged-parent steps on a pull request branch contradict the generated-only procedure. `foundation` starts now. | Two-way | Neither gap touches `foundation`. It has no parent pull request, and the main-merge procedure is the orchestrator's own. The fix reaches `foundation` through its merge of `s-stack-package` before Verify. |
| 2026-11-21 | `foundation-r1`: the shipped `references/status-and-messages.md` states the general code-head rule (exclude `.foundry/`, plus any generated paths a feature plan names) and uses `<id>`, `<feature>` and `<phase>` placeholders. It is not a word-for-word copy of the plan's C2. | Two-way | The generated-files exemption applies to this run only, and the reference ships to every consuming repository. This run's sessions keep using C2 from the feature plan. |
| 2026-11-21 | `foundation-r2`: C2's quoting rule becomes `json.dumps(value, ensure_ascii=False)` if `foundation` shows that it round-trips emoji, accented letters, colons, backslashes and control characters through PyYAML. If it does not, header strings must not contain characters outside the Basic Multilingual Plane. This amends C2 for this run. The feature plan is not edited. | Two-way | Plain `json.dumps` writes an emoji as a surrogate pair, and PyYAML reads that back as two lone surrogates, which then fail UTF-8 encoding. Both reviewers reproduced it. Fixing the rule is better than banning characters, provided a test shows the fix works. |
| 2026-11-21 | Outcome of `foundation-r2`: option A. Header strings must not contain characters outside the Basic Multilingual Plane. | Two-way | `foundation` tested `json.dumps(value, ensure_ascii=False)`. PyYAML refuses DEL (U+007F) and reads NEL (U+0085) back as a space, so the quoting change alone is not safe. Recorded on the phase as `foundation-d2`. |
| 2026-11-21 | Orchestrator merges and hooks in this worktree run with `APM=/Users/samharris/projects/foundry/.venv-apm/bin/apm`. | Two-way | The `apm` on `PATH` is Homebrew 0.35.0, and the hook refuses any version but 0.32.0. This worktree has no `.venv-apm`, and the main checkout's copy is the pinned 0.32.0. |
| 2026-11-21 | `launcher-r1`: C4 gains `launch.sh --print-window`. It takes no other flag, prints `window=<window id>` for the pane in `$TMUX_PANE` and exits 0. It exits 3 when tmux is missing and 1 when the caller is not in tmux. `spec-writer.md` and `orchestrator.md` call it to learn the window and name no tmux command. | Two-way | Every tmux command line stays in `launch.sh`, and nothing silently guesses a window from a subagent or background task that lacks `$TMUX_PANE`. The change only adds to C4. |
| 2026-11-21 | `orchestrator-handbook-r1`: `orchestrator.md` states its own short supervision rules and names no Orchestrate playbook. | 2026-11-21 | `orchestrator-handbook-r2`: C4 gains two modes, `launch.sh --feature <f> --role <r> [--phase <p>] [--update <n>] --close` and `... --remove`. `--close` closes the named session's pane only when that pane is running that session, and otherwise reports and changes nothing. `--remove` removes the named session's worktree only when the worktree is clean and its branch is merged into the orchestrator branch, and otherwise exits non-zero naming the reason. The launcher phase owns both. `orchestrator.md` calls them by flag. | Two-way | It keeps every workmux and tmux command line in the launcher, as `launcher-r1` did. The guards stop the orchestrator closing a pane it does not own or deleting unmerged work. |
| 2026-11-21 | After a CLEAR review, a phase moves to PR. It records minor findings in its evidence file and fixes one only when it would mislead a reader or break a real run. Any fix still means a new code head and both gates again. | Two-way | Fixing minor findings after CLEAR restarts both gates each time, and each new review can raise new minor findings. The roadmap lets a phase leave Review when no significant finding is open. |
