## 13. Idempotency, Existing Files And Bounded Recovery

On every run, inspect before writing. For each intended path: if absent, create only when approved; if identical, no-op; if generated and different, regenerate only from approved sources; if user-authored and different, perform the exact reviewed edit or stop for resolution. Never overwrite an existing application/configuration to match a preferred template. Never reset/clean/stash the user's worktree, force-push, auto-rebase, update submodules or move roots as a repair action.

Use expected-before hashes for controlled edits; write generated outputs atomically after full validation; preserve original user bytes until the replacement is verified. A path created by another process is a conflict. Allow at most two retries for a transient authorised download with the same URL/digest; changed artefacts, repeated failures or new required hosts stop. Do not weaken checksum verification or switch to a floating version. Keep a changed-file ledger and sanitised backups only where authorised; never copy secrets/state into research logs.

On partial failure stop affected dependent tasks. Remove only this run's recorded temporary files after confirming path containment; keep forensic summaries without credentials. Do not automatically delete user files to achieve cleanliness. Local reversal is limited to this run's approved edits with matching expected hashes and user permission. Remote recovery needs the specific approved restoration operation and must not remove stronger controls. No cloud recovery actions are part of setup; never propose reapplying an old plan or restoring state as a generic rollback.

Maintenance runbooks must specify:

- Add app: interview behaviour/owner/runtime; allocate app ID/path; add service-local infra contracts or exact roots; native tests; command entries; source edges; ownership; regenerate maps and run affected checks; no account/backend creation.
- Add module: confirm abstraction/owner/interface/promotion; register local/remote consumers; add fixture validation; update source graph and locks where applicable; run affected consumer checks.
- Add root: confirm target/lifecycle/trust/state identity and collision check; exact source preparation authority; explicit non-deployable or configured-not-connected state; add commands and metadata; no automatic deployment.
- Rename: preserve stable IDs, check old/new graph and state identity, update consumers/docs atomically; stop if backend/source addressing changes outside authority.
- Retire: identify consumers and live-resource ownership first; mark retiring, keep IDs/tombstones and handoff record; remove source only after explicit source-retirement approval and evidence that state/resource responsibility is handled outside this bootstrap. Deleting a directory is not decommissioning.
- Update dependencies/tooling: reviewer verifies provenance/compatibility, checks exact source promotion intent, regenerates only required locks/docs and runs complete affected checks. No automatic merge or deployment.
- Maintain docs: code/interface/command/owner changes update authoritative metadata in the same PR; regenerate maps and commands; validate links and scoped instruction bridges; named owner reviews instructions at the confirmed cadence. Record the source revision or content fingerprint reviewed, avoiding a self-referential “current commit” field that changes on every commit.

## 14. Completion Evidence And Handover

completion.md records plan ID/revision and approval, starting/ending source identities, every file created/changed/preserved, tool versions/digests, check ID/command/cwd/profile/input/result/evidence, warning and blocked details, GitHub desired versus read-back state, actual CI run identifiers if executed, and all deliberately unperformed operations. List the maintenance owner and exact next permitted repository-maintenance actions, not installation tasks for excluded services.

Use four separate status sections: (1) files prepared, (2) local checks actually executed and passed/failed/blocked, (3) GitHub settings actually configured and independently read back, (4) cloud/state/deployment operations not performed and existing controls preserved. Add “remote CI not executed” when only workflow files were checked locally. Do not claim deployment readiness from source validation. A completed local-only scope can be complete while remote configuration remains deliberately excluded; the scope must have been approved that way in advance.

Before handover perform both simulations:

A. Skill-package-only reader with SKILL.md, its required reference files, the deep-interview skill and repository: can it inspect, resolve every mandatory/conditional field, identify safe defaults and obtain precise approval without guessing? Test missing access, no cloud, existing live controls, unsupported feature, absent runtime and private dependency cases. It must stop or generate a fully resolved exclusion, not invent a value.

B. Resolved-plan-only reader: temporarily disregard this skill, its reference files, memo, report and conversation. For each task identify exact input, file, command, version, authority, success condition and recovery boundary from the plan. Missing information invalidates plan approval until fixed. For dynamic runtime inputs, check that binding/validation is complete.

Record the simulation findings, repairs and AT01–AT22 evidence mapping. These are desk reviews unless execution was actually performed. Do not describe a desk review as a tested workflow. Final failure status remains visible when any in-scope required check is blocked. Never manufacture success to finish the checklist.
