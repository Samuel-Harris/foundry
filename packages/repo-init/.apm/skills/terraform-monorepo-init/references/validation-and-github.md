## 9. Tooling And CI Implementation Contracts

### 9.1 Small Baseline And Pinning

Selected baseline capabilities are Git; Python standard-library repository automation; native application tooling resolved per app; Terraform CLI; actionlint when GitHub Actions files are in scope; Gitleaks CLI for secret checks; Dependabot only for supported and authorised update coverage. No additional manager, wrapper, orchestrator, plugin collection, agent framework or duplicate scanner is installed by this skill. Existing out-of-scope tooling is preserved, not adopted or removed implicitly.

`tooling/toolchain.lock.json` has `schema_version`, `tools` and `platform_profiles`. Each tool entry records stable tool ID, exact version, allowed platform assets, official source/release URL, SHA256 or immutable source digest, verification method, version-probe argv, expected probe result, installation path or approved preinstalled identity, maintenance owner and update policy. Pin Actions to full upstream commit SHAs, recording release label for review; verify the SHA belongs to the intended upstream repository. Pin container images by digest if the selected project execution environment uses them. Do not confuse runner image labels with immutable OS images: record the actual runner image and accept its stated reproducibility limit or require an already approved immutable environment.

During instantiation verify compatibility of app/runtime/manager/compiler, Terraform/providers/modules, parser/config formats, action runtime/runner, updater ecosystem and selected agent against the vendors' current documentation, recording each source and check date. Treat every version, support ceiling and feature statement inherited from this skill, a memo or an earlier project as expired until re-checked. Freeze concrete versions before approval. Preserve an existing lockfile unless a specifically authorised dependency change requires it. A lockfile is generated output of selected resolution, not an excuse for silent upgrades.

Downloads: exact approved sources and artefacts only; HTTPS certificate verification on; verify checksum/signature against the recorded official provenance before extraction/execution. Reject archive paths outside the destination. Store local downloads under ignored `.tools/`, build/test outputs under ignored `.artifacts/` or explicit application output paths. No pipe-to-shell downloads, floating tags, curl installer scripts or system-wide changes. If a bootstrap Python runtime is absent, the plan must include the exact authorised platform-specific provisioning method or declare execution blocked pending a supplied environment; it cannot rely on repo.py to install its own prerequisite.

The local and CI versions must match. Commands fail on drift rather than downloading a newer release. Updates require owner review, new provenance/pins, corresponding native lockfile updates and all affected checks. Custom tooling pins not covered by the updater get a named weekly manual review duty. This is maintenance responsibility, not an automatic setup task to update everything.

### 9.2 Application And Configuration Checks

Use selected native package manifests as the source of truth for application dependencies and package scripts. commands.json invokes those script names; it does not repeat internal flags. Freeze dependency resolution with the selected manager's documented lock-enforcing install. Record whether install scripts/postinstall hooks/build backends execute, their exact approval and network needs. If disabling hooks breaks an app, resolve that before approval; do not drop a safety flag during execution.

Each app must have at least one concrete acceptance test for its agreed initial behaviour. Runnable apps need start/stop commands, bind address, port allocation and a smoke assertion; bind only to local/test interfaces, use approved fixture data and terminate only the process created by the test. Interface-only apps need executable schema/contract tests and a truthful “not runnable” README. Separate format check from format write, lint from type checking, and unit checks from integration checks requiring live services. Required integration access outside scope means a blocked check, unless its exclusion was resolved before approval.

All JSON metadata uses the strict in-repo validator. Workflow validation uses the pinned actionlint CLI with explicit file list and `-shellcheck= -pyflakes=` so host-installed auxiliary tools do not change baseline execution. Put shell/Python logic in reviewed source, not large inline workflow programs. These flags disable integrations; they are not installations of extra tools. actionlint validation is not proof of permission safety; run the explicit workflow policy assertions in Section 9.6 and implementation-and-acceptance.md, Section 12, too. App-specific configuration gets the chosen framework/compiler validation, with exact files/commands in the project plan.

Set `.editorconfig`: root=true; UTF-8, LF, final newline, trim trailing whitespace; indentation defined per selected language/formatter. Set `.gitattributes` to normalise text LF and preserve known binary assets; resolve existing conflicting attributes without mass rewriting user files. Do not add a second formatter that fights the first.

### 9.3 Terraform Checks Without Deployment

Register each in-scope root and fixture explicitly. Use a clean disposable copy preserving repository-relative local-module paths, not an isolated root folder that loses its siblings. Exclude `.git`, downloaded directories, local state, backend metadata, secret-bearing files and unrelated user files. Materialise only reviewed generated inputs in the copy. Verify input hashes. Never reuse a developer's `.terraform` directory or remote workspace configuration.

The selected execution profile must keep cloud credentials, SSH agents, host home files, Docker socket and instance metadata credentials inaccessible. Remove inherited TF_CLI_ARGS, TF_WORKSPACE, TF_CLI_CONFIG_FILE, Terraform tokens and provider/cloud credential variables; allow only explicitly declared non-secret environment entries. Use a clean temporary HOME, fresh TF_DATA_DIR and a reviewed CLI configuration without credentials. Keep TF_IN_AUTOMATION=1 and TF_INPUT=0. Do not claim these environment settings alone form a sandbox. Record and verify the actual isolation mechanism. Dependency acquisition can use approved network destinations; subsequent provider execution must use the resolved isolation policy. If offline provider execution with network denied is required, prove that property using the selected platform's mechanism; otherwise stop, never replace it with a prose promise.

Baseline pipeline per root/fixture:

1. Source check: `terraform fmt -check -diff` in the registered directory, with explicit approved file inventory. Run for modules as well without assuming they are deployment roots.
2. For external providers, require a committed root/fixture `.terraform.lock.hcl`. First creation is a separate approved lock-generation operation using exact provider constraints, `terraform init -backend=false -input=false -no-color`, and `terraform providers lock` with the concrete selected `-platform=` arguments. Verify the selected provider identities/checksums and copy back only the authorised lockfile. No `-upgrade` during routine setup verification.
3. Routine validation initialisation in the clean copy: `terraform init -backend=false -input=false -no-color -lockfile=readonly`.
4. `terraform validate -json`. Require command exit zero, parseable supported JSON format and `valid=true`; malformed output is an execution failure. Record warnings rather than suppressing them.
5. Compare source/locks before/after and prove no protected live worktree/state/backend files changed. Module aliases requiring provider configuration are validated through concrete fixture harnesses, not by ignoring missing-alias errors.

For provider-free contract configurations omit lock-generation commands; validate only applicable contracts. Do not add a cloud resource to make a demonstration more convincing. `init -backend=false` skips configured backend access but still acquires dependencies; provider code is not made trustworthy by a checksum alone. Validation is configuration evidence, not a real account/permission/API/deployment test. If a preserved managed/cloud block cannot be validated within the selected offline procedure, mark that exact check blocked or use a separately defined interface fixture, labelled as testing the interface only. Never quietly remove the block and claim the original root passed.

### 9.4 Secrets, Ignore Rules And Ownership

Create `.gitleaks.toml` with `title = "Repository secret policy"` and `[extend]` / `useDefault = true`. No blanket allowlists, baseline suppressions or ignored whole directories. False positives require a narrow, reviewed rule with an owner and rationale. Run the pinned CLI against a sanitised snapshot of all tracked and intended-to-be-tracked files, including dotfiles, using explicit configuration and `--redact=100 --no-banner --no-color --ignore-gitleaks-allow`. Disallow unapproved `.gitleaksignore` entries and clear inherited GITLEAKS_CONFIG variables. The concrete command is `gitleaks dir --config <resolved-config-path> --redact=100 --no-banner --no-color --ignore-gitleaks-allow <snapshot-path>` with paths bound by the runner. Before an authorised first push, also scan the exact outgoing commit range with `gitleaks git` and a validated `--log-opts` range so a secret added and then removed is not missed. No history rewrite or credential rotation is performed automatically. Scanner failures block; report safe metadata only, never the detected secret.

`.gitignore` must exclude `.tools/`, `.artifacts/`, `.terraform/`, `.tfstate`, `.tfstate.`, saved plans, crash logs, `.env`/secret variants, secret variable files, application dependency directories/build outputs, and local credential files. Globally ignore `.tfvars` and `*.tfvars.json`; add only exact, reviewed non-secret exceptions, if needed. Do not ignore `.terraform.lock.hcl`. Exclude application output paths from tracking only after confirming they are generated. Ignore rules do not remove tracked secrets. A separate tracked-file policy check rejects state, plans, secret variable files, credentials and unexpected binaries; verify using filenames and safe content scanning without dumping values.

Generate `.github/CODEOWNERS` from owners and concrete path overrides: repository fallback first, increasingly specific paths after it, automation/AGENTS/metadata controls explicitly owned. List all owners for a pattern on the same line. Validate syntax constraints, path casing and that listed users/visible teams have required repository access when remote verification is authorised. Local generation is not proof of GitHub review enforcement. Preserve existing ownership rules unless edits are authorised.

PR template asks for purpose, changed unit IDs, source dependencies/interfaces, check evidence, generated-doc updates, authority/state impact and deliberate exclusions. A single selected Issues template requests behaviour, expected result, safe reproduction and affected units; no sprawling taxonomy or automatically created labels.

### 9.5 Source-Impact Selection — Deterministic And Conservative

Implement in Python stdlib; no deployment orchestrator. Inputs: validated base/head commit IDs, changed-path/status records, base and head metadata, permitted validation scope. Output: schema version, base/head, selected unit IDs, reasons, deleted/retired IDs, unknown paths, fallback reason and expected check IDs. Stable sorting makes output deterministic. No model decides the set during CI.

Algorithm:

1. Obtain raw NUL-delimited paths/status with Git diff, disabling external diff/textconv. For PRs use merge-base of the actual event base/head for source impact and test the recorded merge revision if the workflow uses one. Union base-to-tested-tree changes where required so changes from the merge are not hidden. Pushes compare event before/after. Merge groups use their event base/head and test that group revision. Validate commit IDs against the actual repository object format; do not hard-code SHA-1 length for repository commits. Action pins still follow their documented upstream commit format.
2. If history/base is missing, a branch is new, or ancestry cannot be established, select all in-scope validation units and report why. Do not make an unapproved fetch. A fetch, if already authorised, is bounded to the approved remote/refs. Do not truncate a large diff.
3. Read both base and head metadata as data. Union mappings and edges, map changed files by source_paths prefixes/exact matches, and seed both old and new paths for renames. Add directly changed units and all reverse-transitive source dependants. A removed edge must still propagate through the old graph. Added units need registration and required checks; missing registration is an inventory failure. Deleted units remain in an impact tombstone until retirement evidence is approved; do not try to execute their missing directory.
4. Include lockfiles, app-package dependencies, application artefacts consumed by roots, templates, generators, generated inputs, root variables and external interface schema/value snapshots. Each app has an enforced source-impact edge to its owned root(s) where the root packages/deploys its artefact; if no such consumption exists, record why. Build prerequisite ordering uses source_dependencies; deployment_after is a separate graph and never triggers deployment.
5. Baseline safety fallback: any changed `.tf`, `.tf.json`, Terraform lock, or module source declaration conservatively selects all in-scope Terraform validation roots/fixtures plus graph dependants. Any metadata, command runner, global lock, workflow, generator or shared config change selects all validation units. An unclassified path selects all and reports an inventory gap, which must be resolved before completion. This intentionally trades CI time for not missing hidden dependencies.
6. Only an explicit docs-only/non-executable classification can avoid app/infra checks. Documentation tests, inventory, generated drift, workflow policy and secret guards still run. All root instructions and scoped AGENTS changes are global policy changes, not harmless docs.
7. Select independently of authority. An affected out-of-scope/live unit is reported, never executed with broader credentials. A required in-scope check that cannot execute is BLOCKED; a pre-approved out-of-scope validation is EXCLUDED with its actual scope, not passed. Source over-selection never increases deployment permissions.

Validate metadata consistency with package manifests, module declarations and declared artefact references during review and the inventory check. The conservative Terraform fallback prevents a missing local-module edge from suppressing Terraform validation, but is not a claim to parse all HCL semantics. Where arbitrary dynamic source/dependency construction defeats reliable classification, mark the path global and require all affected validation; do not implement a brittle regex parser that claims certainty.

Test cases in tooling/tests/test_repo.py and data-only fixtures: direct app change; root-only change; local module consumer; transitive module consumer; shared app package; app artefact to root; provider/package lock change; shared template/generator/input change; unknown path; metadata-only change; docs-only change; new app/root; deleted root/module; removed dependency edge using old graph; rename old/new paths; path with spaces and non-ASCII characters; NUL-safe handling; no base/new branch; merge group; large changes beyond native filter limits; malformed JSON; duplicate state identity; root path traversal/symlink escape; cyclic build graph; stable ID retained after path rename. Expected exact selected set/reasons are asserted, including conservative all-root fanout where required.

### 9.6 GitHub Actions Contract

Default new-repo CI is one always-entered workflow, `ci.yml`, with one stable required check/job `monorepo-ci`. Run selected checks sequentially within that job initially; do not introduce matrix aggregation complexity without a project requirement. If multiple platform jobs are required, the approved plan must specify a final unconditional aggregate job with an exact expected-result set and fail-closed handling of skipped/cancelled/missing children. No path/path-ignore filter on the required entry workflow. Trigger on pull_request events opened/synchronize/reopened/ready_for_review and pushes to the resolved default branch. Add merge_group checks_requested only when the existing/authorised merge queue requires it. No schedule, comment command, pull_request_target, workflow_run or deployment event in the baseline. Draft PR handling is explicitly decided; do not skip a required check silently.

Top-level permissions are empty; only checkout/validation job gets `contents: read`; no id-token/write, secrets inheritance, deployment environment, cloud login or repository write token. Pin every external action by full upstream commit SHA. Checkout uses `persist-credentials: false`, full relevant history, no submodules/LFS unless explicitly required and authorised, and a fresh disposable workspace. Never apply checkout's cleaning/reset behaviour to the developer worktree. Use only a compatible approved runner. GitHub-hosted runner availability, billing and organisation policies must be confirmed; never fall back to a privileged self-hosted runner.

Place all checks in isolated, credential-free child execution profiles resolved in the plan. The GitHub checkout token must not be passed to app installs/tests/providers. Use job secrets nowhere. Treat fork and dependency-bot contributions as untrusted. If private dependency access would expose credentials, do not supply them to untrusted install hooks: resolve a safe prebuilt/offline dependency path or report the required check blocked. Maintainer clicking “approve workflow” is not a grant of deployment authority. A workflow file can be changed in a PR; the file is not a self-enforcing security policy. Protect it through available reviewed controls and least-privilege external configuration, and disclose absent enforcement.

Read event inputs as JSON; never interpolate PR title/body/branch text into shell commands. Use validated IDs/argv arrays and fixed script calls. The workflow invokes the same registered commands as local development. The selector/expected-check logic is read from the trusted base revision where available and treats head metadata as data; changes to control logic require all checks and owner review. At first adoption, the approved exact bootstrap revision is the control baseline. Head-code tests still run in the untrusted sandbox. If a new metadata schema cannot be interpreted by the trusted runner, fail closed and resolve staged adoption, not silently use PR code as authority.

FIXED caching policy: no shared CI dependency/build caches initially. Native lock-enforcing installs in disposable workspaces trade speed for simpler provenance. Do not cache Terraform state, plans, `.terraform` backend metadata, credentials or a previous validation result. The toolchain lock and native locks, not cache hits, identify dependencies. Record this decision as intentional.

Every CI run builds an expected check ledger before executing unit checks. Each result must name the exact source revision/tree, command ID and toolchain. Missing evidence is failure. Required result semantics:

- PASS: required command actually ran, exited as specified, and assertions succeeded.
- NOT_APPLICABLE: selector/approved contract proves that the check does not apply; explain why. A docs-only PR may yield overall success only because all applicable policy/docs checks actually ran, not because a pretend app job passed.
- BLOCKED/NOT_EXECUTED: missing authorisation, dependency, runner or trust boundary; the required aggregate fails or remains genuinely pending awaiting platform approval, never green/neutral.
- FAIL/ERROR/TIMED_OUT/CANCELLED: not success. Fail closed; do not use continue-on-error, `|| true`, or job-skipping as a required-check shortcut.
- GitHub has not executed a workflow because activation/approval is absent: report “not executed”, not “CI passed locally”.

The single job runs repo.py ci, preserving nonzero failures, with a final `if: always()` summary/completeness check. Do not let the final step overwrite earlier failure. Bound workflow/job/command timeouts with actual numeric values in the project plan. Cancelling superseded validation-only runs may be confirmed; do not alter concurrency/cancellation of existing deployment workflows.

### 9.7 Dependency Updates

If Dependabot is selected and its activation authorised, create `.github/dependabot.yml`, version 2, with github-actions directory `/`, interval weekly, and explicit supported package/root directories. Confirm the actual ecosystem versions and private-source support. Reusable modules with independent manifests/source references also need coverage, not just runtime roots. Use no auto-merge and no unapproved registry secrets. Record owner and review process. Validate the generated configuration against a pinned supported schema/explicit implemented field rules in repo.py; actionlint is not a Dependabot schema validator.

If updater activation is not authorised, do not place a triggering file on an activated branch. Local selected-but-inactive configuration belongs under tooling/prepared/github and is labelled preparation only. If the service itself is not selected, create no configuration; the approved manual owner/cadence covers updates. If a bot cannot maintain toolchain.lock.json or exact provider hash sets, the maintenance command/owner does. Never claim an update PR alone verifies provider locks, module promotion or application compatibility.

## 10. Separately Authorised GitHub Configuration

Create a settings matrix with columns setting, observed/effective value, desired value, primary-doc feature requirement, repository evidence, exact delta, operation ID, verification evidence and status. Statuses distinguish prepared, configured-and-read-back, unavailable, not-authorised, unchanged and blocked.

Assess default branch; Actions allowed sources and effective token permissions; fork execution approval; required checks and their originating application; branch/tag rules; review count and code-owner review; stale approval handling; force-push/deletion/bypass policy; merge methods; existing merge queue; updater configuration; visibility; Issues. Deployment environments/gates/credentials are inventory-only, not setup changes. Never create a protection on a guessed branch or remove an existing control to install a preferred one.

As observed at the 13 September 2026 source check, primary documentation made branch rules/CODEOWNERS feature availability dependent on visibility and plan, and restricted environment required reviewers on Free/Pro/Team to public repositories. Both the restrictions and the plan names may since have changed, so treat those statements as expired examples and establish the exact current feature/account/organisation support by reading the documentation at instantiation. Do not infer that a private Team repository having branch protection also has private environment approval gates. CODEOWNERS requires eligible owners and configured enforcement; multiple owners on one line do not require all owners to approve. Resolve multi-party approval requirements explicitly or report unsupported enforcement.

Before any approved remote change: re-read effective settings, confirm before-state matches the approved plan, confirm actor capability, inspect activation listeners, execute only the exact payload/UI steps, then read back effective state including inherited policy/bypass actors. Do not report configured on the basis of a file or a successful write alone. If a check must first run before becoming selectable as required, resolve the initial CI activation/order in advance; do not create a fictitious required check or weaken old checks temporarily. Remote test PRs and negative merge tests require their own authority. Without it, read-back evidence can establish settings, but enforcement experiments remain unexecuted.

If a desired control is unavailable/unauthorised, ask for explicit acceptance of a precisely described unenforced local-only scope, or leave that work blocked. Never silently replace it with a README warning and call it equivalent. No subscription purchase, organisation policy change or source-access grant is implied.
