# Phase `integration` checks

Phase `integration` makes the `sam-mode` handbooks agree with each other and with `references/status-and-messages.md`, and puts the adopted gate-cost rules into the handbook text. A session follows several of these files at once, so each behavioural check is a cold read across the files that must agree. A cold read starts a fresh subagent, gives it only the files the check names and the scenario the check quotes, tells it to read nothing else, and asks the questions. Its answer passes when it agrees in substance with every point of the expected answer. Wording may differ, but a missing or contradicting point fails the check. Wait for every cold-read subagent to finish before reporting.

The checks of the other phases' files cover the rest of this phase's fixes: `foundation.md` cold read 3 and its two scripts the code head, the merge rule and the orchestrator's messages, `phase-handbooks.md` the scoped Verify after a conflicted merge, and `orchestrator-handbook.md` the recorded `pushed` heads and the scoped post-merge check. Every scenario below uses placeholder data. The files, relative to the repository root, under `packages/s-stack/.apm/skills/sam-mode/`:

- `references/status-and-messages.md`, the reference
- `handbooks/phase-session.md`, `handbooks/verifier.md`, `handbooks/reviewer.md`, `handbooks/pr-creator.md`, `handbooks/orchestrator.md` and `handbooks/planner.md`

## Rerun

### Cold read 1. Waivers, baselines and the merge rule across the gate handbooks

Files: the reference, `phase-session.md`, `verifier.md` and `reviewer.md`.

Prompt: "Read only these four files and nothing else, not even files they link to. Answer from them and the scenario alone. You are the phase session for phase `widgets`. Your status file's `verdicts` are, oldest first: verify `VERIFIED` at code head `aaaa…`, then review `SIGNIFICANT` at `aaaa…`, whose finding was that `python3 tools/w.py parse ''` exits with a traceback. You then committed `bbbb…`, which changes the parsing logic in `tools/w.py` to accept an empty row, and the code head is now `bbbb…`. (1) For Verify at `bbbb…`, what does the verifier's brief say about its baseline and about waiving, may the verifier waive this change, and what does it run? (2) For Review at `bbbb…`, what is the scope, what does every reviewer get from the earlier review, how many reviewers start first, and may the first one waive? (3) Suppose instead the verdicts after the first two were verify `WAIVED` at `bbbb…` and review `WAIVED` at `bbbb…`. Does the merge rule hold, and may the phase move to PR? (4) Later the verdicts end with verify `VERIFIED` and review `CLEAR`, both at `cccc…`. You commit `dddd…`, which fixes a typo in a code comment that no test asserts. Which gate agents may waive, what do you record, and may the phase reach PR on those verdicts? Then you commit `eeee…`, which changes a function's control flow. What does Verify cover, and what does Review cover? (5) A commit changes only a skill file that agents follow. May the verifier waive it? If something could observe the change but no check can run in the verifier's environment, what is the verdict?"

Expected answer:

1. The brief names `aaaa…` as the code head of the newest `VERIFIED` verdict and says the verifier may waive, because the verify gate's newest verdict that is not `WAIVED` is `VERIFIED`. The verifier still may not waive this change, because a change to logic or control flow is never waivable. It runs the checks in the blast radius of the phase's own work since `aaaa…`, here `bbbb…`, and no check outside it.
2. The scope is the phase's own work since `aaaa…`, the code head of the most recent `CLEAR` or `SIGNIFICANT` review: each first-parent, non-merge commit after it outside `.foundry/`, plus the conflict resolution of any merge. Every reviewer gets the earlier finding's command as a probe to run again at `bbbb…`, and a probe that still fails is a significant finding. One reviewer starts first, on one model family, and its brief says it is first and may not waive, because the review gate's newest verdict that is not `WAIVED` is `SIGNIFICANT`. It reviews, and the second adversary then starts on the other model family. An answer under which the first reviewer may waive here fails this point.
3. No. The verify waiver counts, because the newest earlier verify verdict that is not `WAIVED` is `VERIFIED`. The review waiver does not count, because the newest earlier review verdict that is not `WAIVED` is `SIGNIFICANT`. The merge rule fails, so the phase may not move to PR. An answer that lets the phase reach PR fails this point.
4. Both the verifier and the first reviewer may waive: their briefs say they may, because the newest verdicts that are not `WAIVED` are `VERIFIED` and `CLEAR`, and a comment change no test asserts is waivable. The phase session records each `WAIVED` as the verdict for `dddd…`, with its reason in the evidence file, and moves on to Review and then PR, because the merge rule holds at `dddd…`. A waiver never moves a baseline, so at `eeee…` Verify covers everything since `cccc…`, both `dddd…` and `eeee…`, and Review also covers everything since `cccc…`. An answer that starts either scope at `dddd…` fails this point.
5. No. A change to instructions an agent follows, such as a skill or handbook, is never waivable. When something could observe a change but no check can run, the verdict is INCONCLUSIVE, not `WAIVED`, and INCONCLUSIVE is not a pass.

### Cold read 2. Waiting, answers and merges of the orchestrator branch

Files: the reference and `phase-session.md`.

Prompt: "Read only these two files and nothing else, not even files they link to. Answer from them and the scenario alone. You are the phase session for phase `widgets` of feature `demo`. (1) While you build the phase in Implement, you find that your feature plan entry says the export writes CSV, while the roadmap's `README.md` says it writes JSON. What do you do, which keys of your status header change, and in what order do you commit and send? Do you change the feature plan yourself? (2) The orchestrator sends `answer` for that request. What do you do? (3) Before Verify, merging the orchestrator branch conflicts in `src/gadgets/api.py`, a file that phase `gadgets` owns. What do you do, what do you commit before you send anything, and when does `waits_for` change again? (4) Another time, merging the orchestrator branch is clean and brings in phase `gamma`'s code. Does your code head move, and does the merged-in code need your gates? The orchestrator branch tracker's 'Merged phases' table shows that `gamma`'s post-merge check failed, in a module your phase builds on. What changes for your gates? (5) The orchestrator sends you a `move-back` to Spec, because a roadmap update touched your phase. What do you do, what do you wait for, and what do you do when that arrives?"

Expected answer:

1. The roadmap wins. The session commits a decision request to `requests` with its question, options, recommendation, door and waiting work, naming both texts, and, if work waits on it, sets `waits_for` to one line saying what for in that same commit. Only then does it send the orchestrator a `decision-request` message. It does not change the plan itself.
2. It removes the request from `requests`, records the outcome in `decisions`, sets `waits_for` back to `null` if the answer ends the wait, commits, and continues the work that waited. An answer that leaves the request in `requests` fails this point.
3. A conflict in a file another phase owns is not its to resolve. It aborts the merge, commits `waits_for` with one line naming what it waits for, and then sends a `blocked` message that names the file, and waits. It sets `waits_for` back to `null` in the commit that ends the wait.
4. A clean merge of the orchestrator branch does not move the code head, and the code it brings in counts as verified and reviewed, so the phase keeps its state and verdicts. Because the newest post-merge check failed in something the phase builds on, the session treats the merged-in code as its own: it names that failed check, and the merge, in the verifier's and the reviewers' briefs.
5. It commits what it has, stops the work the change could invalidate, records state Spec with `waits_for` set in that commit, and sends `state`. It waits for a `move-back` to Plan, which the orchestrator sends once the planner has revised the plan. Then it merges the orchestrator branch, updates the phase plan against its entry, which may be unchanged, commits it, clears `waits_for`, and moves to Implement.

### Cold read 3. A PR creator round from both sides

Files: the reference, `phase-session.md` and `pr-creator.md`.

Prompt: "Read only these three files and nothing else, not even files they link to. Answer from them and the scenario alone. The default branch is `main`. Phase `widgets` is in Review. Its status file's `verdicts` end with verify `VERIFIED` at `cccc…`, then verify `WAIVED` at `dddd…`, then review `CLEAR` at `dddd…`, and its code head is `dddd…`. Its `pull_requests` are #31 on branch `widgets-a`, which has merged, and #32 on branch `widgets-b`, which is open. Its `pushed` is `\"widgets-a=1111111,widgets-b=2222222\"`. (1) Does the merge rule hold, and may the phase move to PR? (2) As the phase session, what does your PR creator's brief give it? Name the orchestrator branch, `OWN` and `PUSHED` exactly. What does the PR creator check before anything else? (3) The PR creator reports that the proof printed `FAIL docs/w.md differs between the phase and main and no open pull request holds it: ...` and `NOT EQUAL`, and that nothing was pushed. Only commits that landed in #31 changed `docs/w.md` on the phase. What does the phase session do, and does it send `prs-open`? (4) A later round reports `EQUAL`, every push succeeded, and `RECORD widgets-a=1111111,widgets-b=2222222,widgets-b=4444444`. What exactly does the phase session record and send? (5) Later the orchestrator sends an `instruction` to refresh #32, naming its recorded head `4444444` and its current head `5555555`. What does the phase session do? The PR creator then reports `DEVELOPER-COMMITS widgets-b 5555555`, where `5555555` is a merge the developer made that also edits `docs/w.md` by hand. What happens next, and what if the report had been `EQUAL` instead? (6) In a round, the regenerate command raises a package's version to `0.4.2`, but another open pull request already ships `0.4.2` of that package and a third ships `0.4.3`. What does the PR creator do?"

Expected answer:

1. Yes. The verify waiver counts, because the newest earlier verify verdict that is not `WAIVED` is `VERIFIED`, and the review verdict is `CLEAR`. Both name `dddd…`, the current code head, so the merge rule holds and the phase moves to PR.
2. The absolute path of `pr-creator.md`, the roadmap, the feature plan, the phase plan, the status file, the phase branch, and the local orchestrator branch, never `origin/<orchestrator branch>`, which may lag or not exist. `OWN` is `widgets-a,widgets-b`, the merged branch included. `PUSHED` is `widgets-a=1111111,widgets-b=2222222`, the status file's `pushed` unchanged. The PR creator first checks the reference's merge rule for the current code head, which holds, so it goes on. An answer that drops `widgets-a` from `OWN`, or has the PR creator refuse the `WAIVED` verify verdict, fails this point.
3. It sends no `prs-open`. The default branch changed the path, so the phase session merges `origin/main` into the phase branch with `git merge --no-ff`, keeping the default branch's version. That merge is allowed on the phase branch's first-parent line. It moves the code head, so the phase passes the gates the new code head needs, then starts a PR creator round again. No new pull request is opened for it.
4. It records #31 and #32 in `pull_requests` and sets `pushed` to `widgets-a=1111111,widgets-b=2222222,widgets-b=4444444`, the `RECORD` line without the word `RECORD`, exactly as printed. It commits, then sends `prs-open` with each number and its `depends_on` list, the code head, and that `pushed` line.
5. A refresh instruction asks for a PR creator round, not new work, so in PR it starts a PR creator round and acts on the report. On `DEVELOPER-COMMITS` it runs the feedback round: it moves back to Implement, and because the developer's commit is a merge with hand edits, it makes an ordinary phase commit that gives `docs/w.md` the merge's content instead of cherry-picking. It passes Verify and Review again for the new code head, then runs a PR creator round, and the `prs-open` it sends answers the round. Had the report been `EQUAL`, the phase stays in PR, no gate runs again, and it records the new `pushed` line and sends `prs-open`.
6. It sets the `version:` line one patch above the highest open version, `0.4.4`, runs the command again so the lockfile follows, and keeps both in the one regenerate commit, so no two pull requests ship the same version.

### Cold read 4. The orchestrator's decisions, failed merges and the full run

Files: the reference and `orchestrator.md`.

Prompt: "Read only these two files and nothing else, not even files they link to. Answer from them and the scenario alone. You are the orchestrator of feature `acme-widgets`, default branch `trunk`, window `@9`. The feature plan's phases are `alpha`, `beta` and `gamma`. It names the generated paths `**/lock.json`, the regenerate command `make lock` and the repository checks `make check`. Say exactly what you do in each case. (1) `acme-widgets-phase-beta` sends `blocked`: merging the orchestrator branch conflicts in `src/gamma/api.py`, which phase `gamma` owns. `beta`'s `waits_for` says it waits on that conflict, and it is quiet. (2) The developer answers `beta-r1` with an option that changes a contract in the feature plan. (3) In this tick `origin/trunk` is at `t5t5…`, which you have not merged. The merge applies without conflict, but `make check` fails. What do you do, and what happens in the next tick if `origin/trunk` is still `t5t5…` and the developer has not answered? (4) You merge `gamma`, the last phase of the feature plan to merge, and its post-merge check passes. What else happens because it was the last? That run then fails in a check on `src/alpha/`, which `alpha` owns. (5) In another tick you merge `beta` again, at a new code head. Its only new work since its last merge is the resolution of a conflict with the orchestrator branch, whose code the orchestrator branch already holds, so this merge's first-parent diff changes only `packages/x/lock.json`. Which post-merge check runs, and does the architecture page change? (6) After two of the feature's pull requests merged into `trunk`, `trunk`'s checks fail, and only on generated content. (7) Pull request 33 is a draft. Its head contains `origin/trunk`'s tip and the current head of the open pull request it depends on, and every required check passed on that head. Is it flagged with `needs_update`? (8) Every phase is Done, and no full run of the verification skill has passed since the last phase merge. What ends the feature, in what order?"

Expected answer:

1. A `blocked` that names a conflict in another phase's file goes to the developer as a decision request, naming the owning phase `gamma` and the path, listed in the tracker and under **Needs you**. `beta` has not stalled, because its `waits_for` is set. The orchestrator does not resolve the conflict.
2. It records the decision in `run-decisions.md` with its date, door type and reason, commits it, and sends `answer` to `beta`. Because the answer changes the feature plan's contract, it restarts the planner with an `instruction` that names the decision and the phases it affects. When the planner sends `done-planning`, it checks that the branch changes nothing outside `.foundry/plans/`, merges it with `--no-ff`, closes the planner's pane, writes the board's `phases` documents, starts each phase whose dependencies are met, and sends `move-back` to Plan to each started phase whose entry the message names as changed.
3. It aborts the merge, tells the developer, and records the tip `t5t5…` in the tracker. It does not merge that tip again until the developer answers or the default branch moves, so in the next tick, with `origin/trunk` still at `t5t5…` and no answer, it does not try the merge. `t5t5…` is not recorded as merged.
4. It sends `merge-orchestrator-branch` to every other live phase that has not reached PR and starts any phase whose dependencies are now met. Because `gamma` was the last phase to merge, a fresh subagent runs the whole verification skill on the orchestrator branch. When that fails, the orchestrator branch is frozen until a later check passes, and `alpha`, which owns the failing paths, gets a `move-back` to Implement naming the failed check. While frozen it starts no new phase, merges no other phase and not the default branch, and sends `merge-orchestrator-branch` to no phase.
5. None runs: a merge that changes only generated paths needs no check, counts as passing, and the tracker records that none was needed. No waiver is involved. Because the merge passed in this sense, a fresh subagent updates the architecture page, and the other live phases that have not reached PR get `merge-orchestrator-branch`.
6. This is one of the histories handled by asking. It records what it saw in the tracker, stops acting on every phase it touches apart from reconciling it and keeping the board current, and sends the developer a decision request with the options it sees and its recommendation. It acts on those phases again once the developer answers.
7. No. An open pull request, draft or not, is up to date when its head holds the default branch's tip and the current head of every open pull request it depends on, and every required check has passed there. Being a draft does not flag it.
8. A fresh subagent runs the whole verification skill on the orchestrator branch and the result goes in the tracker; a failure is handled as a failed post-merge check, with a `move-back` to Implement. Only once a full run has passed does a fresh subagent update the architecture page a last time, the tick is deleted, every pane it started is closed with `--close`, each branch's last status commits are merged, every remaining worktree is removed with `--remove`, and the developer is told the feature is complete.

### Cold read 5. Two kinds of dependency in the planner's phase entries

Files: `planner.md` only.

Prompt: "Read only this file and nothing else, not even files it names or links to. Answer from it alone. You are the planner. The approved roadmap has three phases. `schema` adds a database table under `db/`. `api` builds endpoints under `server/` on that table, so it needs `schema`'s code on the orchestrator branch. `client` changes `web/` and installs the `server` package from the published registry, which publishes only from the default branch, so it can start only once every pull request of `api` is merged into the default branch. Write the **Depends on** field of each phase's entry."

Expected answer:

1. `schema` depends on none.
2. `api` depends on `schema`, and the entry says it must be merged into the orchestrator branch before `api` starts.
3. `client` depends on `api`, and the entry says `api` must be Done, with every pull request merged into the default branch, not only merged into the orchestrator branch. An answer that does not say which kind each dependency is, or gives `client` only an orchestrator-branch dependency, fails this point.

### Cold read 6. A scoped run of the verification skill

Files: `tests/s-stack/verify-s-stack/SKILL.md` only.

Prompt: "Read only this file and nothing else, not even files it names or links to. Answer from it alone. You are the fresh subagent an orchestrator started for a post-merge check. Your brief says the blast radius holds only 'Cold read 3' of `checks/foundation.md`, and that every other check file's checks are outside it because none of the files they read changed. The directory holds the check files `board.md`, `foundation.md` and `launcher.md`. (1) Under check 8, which checks do you run, and what do you report for the other check files? (2) When are all the `## Rerun` checks run? (3) `Cold read 3` reports PENDING because a file it needs is missing on this branch. Does that fail the verdict?"

Expected answer:

1. Only `Cold read 3` of `checks/foundation.md`, exactly as written, compared with its expected result. No other check of `foundation.md` runs, and every other check file, `board.md` and `launcher.md`, is reported with the brief's reason, not run. An answer that runs every Rerun check fails this point.
2. The full run, every Rerun check in name order, is for the end of the feature and for when the developer asks.
3. No. A Rerun check may report PENDING when what it needs is absent on the checked-out branch, and PENDING never fails the verdict. It is named beneath the verdict.
